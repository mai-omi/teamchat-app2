# 権限・ルーティング・公開API設計

`features.md`・`questions.md`・`screens.md`・`data.md` と、`spec.md`・`mockup/` を根拠に作成。
根拠の書き方は他のファイルと同じ：`spec.md n-n` ／ `mockup/ファイル名` ／ `questions.md Q-n` ／ `features.md F-n` ／ `screens.md SC-n`。

## 1. 権限マトリクス

行は `features.md` のF-01〜F-31。列は利用者の区分。

利用者の区分は4つ。3・4列目は「ある1つのチャンネルについて」の関係であることに注意（例：Aさんが作ったチャンネルの列では「作成者」はAさんだが、Bさんが作った別のチャンネルの列ではAさんは「メンバー」または「社員（無関係）」になる）。

- **未ログインの人**
- **ログイン済みの社員**（対象チャンネルと関係がない、または対象チャンネルが存在しない機能の場合）
- **対象チャンネルのメンバー**（プライベートチャンネルに追加された人。作成者を除く）
- **対象チャンネルの作成者**

対象チャンネルが存在しない機能（F-01〜F-03、F-23、F-27〜F-31）では、3・4列目は2列目と同じ扱いになる（ログイン済みであれば、チャンネルとの関係を問わない）。

### ―（権限の対象外）の内訳

F-05・F-10・F-14・F-18・F-19・F-21・F-22・F-24・F-25・F-26・F-29・F-30・F-31 は、`data.md` のCRUD表で独立した操作を持たなかった行と同じ理由で、独立した権限判定も持たない（他のF-IDの操作に含まれる、または画面の見せ方・絞り込み条件にとどまる）。詳細は `data.md` 4.を参照。

### △の条件

- **F-13（メンバーの削除）作成者列**：外す対象が自分（作成者自身）以外のメンバーであること。作成者は自分自身を外せない（`mockup/members.html`「作成者は外せません」／`questions.md`「Qに対応しない回答」3.）。
- **F-15・F-20（投稿・返信）社員列**：投稿先・返信先が公開チャンネルであること。プライベートチャンネルで自分がメンバーでない場合は不可（`spec.md 3-2`・3-3、`data.md` F-09）。
- **F-16・F-17（メッセージの編集・削除）全列**：自分が書いたメッセージであること。チャンネルの作成者であっても、他人のメッセージは編集・削除できない（`spec.md 3-4`「自分が書いたメッセージは...他の人が書いたメッセージは直せません」）。加えて、社員列は投稿先チャンネルへの閲覧権があることが前提（自分が書けた場所でなければ、そもそも編集対象にならない）。

### 検索・公開APIがこの表に入らない理由

F-23（検索）とF-27・F-28（公開API）は、上の表では全列が○になっている。だが、これは「検索を実行できるか」「APIを呼び出せるか」という入口の話が全員○なだけで、**この2つが何も守っていないという意味ではない**。○×△の表だけを見ると、全部埋まっているので安全に見えてしまうが、実際の防御はこの表の外（＝返す中身の絞り込み）で行っている。

この表が答えているのは「だれが、その操作を実行できるか」であって、「実行した結果、何が見えるか」ではない。検索と公開APIは、**実行自体は誰でもできるが、返ってくる内容がその人・その呼び出し元ごとに絞り込まれる**という、表の軸とは別の守り方をしているため、そのままでは表に収まらない。

- **検索（F-23）の守り方**：検索を実行すること自体は、ログイン済みの社員なら誰でもできる（○）。守っているのは実行の可否ではなく、**結果に出すメッセージの絞り込み**（F-25）で、検索した人が閲覧できるチャンネル（公開チャンネル＋自分がメンバーのプライベートチャンネル）のメッセージだけを対象にする（`spec.md 3-6`「検索結果に出てよいのは、その人が見られるチャンネルのメッセージだけです」、`data.md` CRUD表のF-23行で`channel_user`・`channels.type`をRして判定）。
- **公開API（F-27・F-28）の守り方**：APIを呼び出すこと自体は、ログインの有無を問わず誰でもできる（○。むしろ未ログインのために用意したAPI）。守っているのは呼び出し元の区別ではなく、**返す内容を`channels.type = public`のものだけに絞り込むこと**（F-29）。プライベートチャンネルを指定された場合は、存在そのものを伝えないよう404で返す（`permissions-api.md` 3.）。

つまりこの2つは、「表の○×で守られている」のではなく、「表の○は入口が開いていることを示すだけで、本当の防御はSQLの絞り込み条件（WHERE）とレスポンスの組み立て方にある」と読む必要がある。

## 3. 公開APIの設計

`spec.md 3-7`「用意してほしいのは次の2つです」のとおり、読み取り専用の2本のみ。認証不要、書き込み系APIは用意しない（F-29）。

### GET /api/channels

**概要**：公開チャンネルの一覧を返す（F-27）。

**リクエスト**：パラメータなし。

**レスポンス（200）**：公開チャンネル（`type = public`）のみを配列で返す。プライベートチャンネルは、件数も含めて一切出さない（`spec.md 3-7`「プライベートチャンネルの情報は...いっさい含めないでください」）。

```json
[
  { "id": 1, "name": "全体連絡", "description": "全員に共有したいこと" },
  { "id": 2, "name": "開発", "description": "開発に関する相談と報告" },
  { "id": 3, "name": "雑談", "description": "なんでもどうぞ" }
]
```

フィールドはチャンネルの名前・説明のみとした（`mockup/channels.html` の一覧表示項目のうち、外部に見せる必要があると仕様書から読み取れる最小限。「作成者」は内部の管理用の項目であり、`spec.md 3-7` はチャンネル一覧としか言っていないため含めていない。この選定は仕様書に明記が無く、こちらで決めたものなので、6.で指摘する）。

### GET /api/channels/{channel}/messages

**概要**：指定した公開チャンネルのメッセージ一覧を返す（F-28）。

**リクエスト**：パスパラメータ `channel`（チャンネルID）。ページングは設けず、全件返す（`questions.md` Q-10）。

**レスポンス（200）**：

```json
[
  {
    "id": 101,
    "author": "鈴木 花子",
    "body": "おはようございます。9月リリースの日程を今週中に確定させたいです。金曜の夕方までに、残っているタスクを各自共有してもらえますか。",
    "posted_at": "2026-08-17T09:12:00+09:00",
    "edited": false
  },
  {
    "id": 102,
    "author": "高橋 健",
    "body": "承知しました。検索まわりの実装は木曜に終わる見込みです。",
    "posted_at": "2026-08-17T09:20:00+09:00",
    "edited": true
  }
]
```

（本文は `mockup/channel-show.html` の実際の投稿を例にした）

- 削除済みのメッセージは、結果に含めない（`questions.md` Q-11「含めないでください。外から見えるところに『削除されました』が並ぶ必要はありません」）。
- 編集済みのメッセージは `edited: true` を付けて含める（`questions.md` Q-11）。
- 並び順：画面（SC-04）と同じ、投稿日時の古い→新しい（`questions.md`「Qに対応しない回答」6.からの類推。公開APIそのものの並び順は仕様書に明記が無いため、6.で指摘する）。

**エラー（404）**：指定したチャンネルが存在しない場合と、存在するがプライベートチャンネルである場合の、両方を同じ404として返す。

```json
{ "message": "指定されたチャンネルが見つかりません" }
```

プライベートチャンネルのときに403（権限エラー）を返すと、「そのIDのチャンネルは存在する」ことが外部に伝わってしまう。`spec.md 3-7`「チャンネル名も含めて、いっさい含めないでください」の徹底のため、存在しない場合と区別せず404にする。

## 4. 認証が必要な画面でのエラーの返し方（概要）

詳しい例外方針は `behavior.md` に書く。ここでは公開APIとの違いだけ示す。

| 状況 | 公開API（JSON） | ログイン後の画面（Blade） |
| :-- | :-- | :-- |
| 権限が無い操作 | 該当なし（公開APIは読み取り専用で、権限分岐が無い） | `behavior.md` 3.参照 |
| 対象が見つからない | 404 + JSON（3.参照） | `behavior.md` 3.参照 |
| 入力値が不正 | 該当なし（公開APIは入力を受け取らない） | `screens.md` 4.の各画面の表のとおり |

## 5. 権限マトリクス・ルーティングを書いて気づいたこと

- F-13の「作成者は自分自身を外せない」は、`data.md` のCRUD表では権限の話として表から外したが、権限マトリクスでは△の条件として書く場所がある。両方の文書を見ないと全体が分からない構造になっているので、読む順番（`data.md` → この文書）を覚えておく必要がある。
